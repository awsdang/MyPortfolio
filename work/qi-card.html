CASE FILE 01 · QI CARD / SUPERQI · FINTECH DISTRICT

Billing that makes sense the first time.

RoleSenior Software Engineer, Billing Team Period2024 to present · promoted March 2026 SurfaceTasdid+ · Jabi+ · e-Psule Result3 production products · 1M+ users · 3 languages

§1 CONTEXT

A million people use these products. Many are over 50 and just want the bill in front of them to make sense.

Qi Card is Iraq's largest fintech. I work on three products inside SuperQi, which uses Alipay's mini-app platform and APIs. Tasdid+ is a billing and invoicing system. Jabi+ gives merchants statements, salaries, supplier payments and Excel export from a phone. e-Psule is a billing app for the Kurdistan Region in Kurdish, Arabic and English.

I cannot share payment-rail internals, so this page focuses on the product and engineering decisions.

§2 THE CONSTRAINTS

  • The product had to feel obvious to normal people, often over 50 and using it for the first time.
  • It still had to work on low-end Android phones and unreliable networks.
  • Multiple bill providers with wildly different response times and failure behaviours.
  • The UI can have a visual bug. It can never guess what happened to someone's money.
  • Hard bundle-size budgets inside the super-app runtime.
  • Every flow passes internal security review; payments run on wallet and tokenization-supported card rails.
  • Kurdish, Arabic and English had to work from the start, including right-to-left layouts.

§3 MY OWNERSHIP

  • I designed and built the Svelte/SvelteKit frontend architecture inside the Alipay mini-app runtime.
  • I built bill inquiry, invoices, payment selection and provider-specific error states.
  • I added caching and progressive loading so the useful parts show up first.
  • I integrated wallet and tokenization-supported card payments through security review.
  • I shipped filtering, sorting, pagination and Excel export for Jabi+.
  • I delivered e-Psule in Kurdish, Arabic and English.

§5 KEY DECISIONS

Separate UI state from transaction state.

The app can crash, reload or lose the network and still recover. It never invents a payment result. The state machine owns that truth.

Svelte for the phones people actually own.

Svelte gave us a small bundle and fast cold start. That mattered more than framework preference.

Progressive loading over spinners.

Providers answer at different speeds. The screen fills in as responses arrive instead of waiting for the slowest one.

Provider errors stay distinct.

A timeout, invalid account and provider outage are different problems. The user gets a useful message for each one.

Merchant tools don't assume a laptop.

For many merchants, the phone is the whole back office. Jabi+ keeps large datasets usable on a small screen and still exports to Excel when the accountant needs it.

§7 FAILURE MODES, HANDLED

Provider timeout

Distinct state with its own copy and retry path; the rest of the screen keeps working.

Payment pending

The UI says pending. It never guesses success. The final answer comes from the source of truth.

User cancels mid-flow

Transaction state machine unwinds cleanly; no orphaned intents.

Slow network

Cache serves the last known state instantly; the network upgrades it when it can.

§8 SCREENS

These screens use fake names, amounts and accounts. No customer data is shown.

§9 WHAT I LEARNED

Payments are better when they are boring. Clear states, small bundles and careful reviews make that possible.

§10 WHAT I'D CHANGE TODAY

I would define a shared latency budget for every provider before product design starts. Then each new mini-app would inherit the same progressive-loading behaviour instead of deciding it again.
